# 为什么越来越多的人抛弃 MCP，转向 CLI？

MCP 曾被誉为 Agent 的万能接口，是连接一切工具的标准。但最近越来越多顶级开发者开始悄悄抛弃它，转而用更原始的方式解决问题：直接调用命令行程序。

转换视频格式，一行 `ffmpeg`；搜索文件，一行 `grep`；调整图片尺寸，一行 ImageMagick。这些工具有一个共同点——通常在命令行界面（Command Line Interface，简称 CLI）里执行，因此也被称为 CLI 工具。

这不是极客小圈子自嗨。今年 3 月，Perplexity 的 CTO 在开发者大会上公开宣布，他们内部正全面转向 API 和 CLI，放弃 MCP；Y Combinator 的 CEO 也选择用 CLI 而不用 MCP；最近爆火的 OpenClaw，实际执行任务时几乎全是内部工具和 CLI 命令，基本看不到 MCP 的身影。

问题随之而来：MCP 明明是专门为大模型设计的工具接口标准，为什么反而被古老的 CLI 抢了饭碗？CLI 有什么优势，MCP 又有什么短板？谁才是大模型工具的未来？

## CLI 的优势一：Token 消耗更小

CLI 受青睐，主要有两点：Token 消耗小，执行效率高。先说 Token。

反过来说，就是 MCP 的 Token 开销大——尤其是工具元信息：名称、描述、入参格式等，都会塞进大模型上下文。

举个例子。假设你想了解 OpenClaw 仓库最近有哪些 bug，向模型提问：「OpenClaw 这个 GitHub 仓库最新的 3 个 issue 是什么？」发给模型的不只是用户问题，还有可用的 MCP 工具列表（如 `list issues`、`create branch`），好让模型选出相关工具并调用。这些列表通常由 Claude Code、Codex 这类程序代发。

关键在于：列表里不只是工具名，还包括每个工具的详细说明——能干什么、要传哪些参数、参数格式是什么。以 GitHub MCP Server 为例：

| 项目 | 规模 |
|------|------|
| 单个工具说明（如 `list issues`） | 约 67 行 |
| 全部工具数 | 44 个 |
| 全部元信息 | 约 1683 行、63703 字符 |
| Token 占用 | 约 **14268** tokens |

按 Claude Sonnet 计价，仅这一份工具说明大约 **0.3 元**。这还只是一个 GitHub MCP Server；若同时挂多个同类 Server，光工具说明就能花掉好几块钱——还没算模型输出费用。

换成 CLI，流程类似，但只需暴露一个 `bash`（或等价）工具：说明大约十几行，核心就是传入 `command` 参数，由模型生成要执行的命令。例如用 `gh` 拉取 issue 列表。相对上万行的 MCP 说明，Token 几乎可以忽略。

模型怎么知道 `gh`、`git`、`grep` 这类命令？常见 CLI 在训练阶段就见过大量用法，天然会用——就像老程序员不用翻文档也能报出 git 命令。若是冷门或自研 CLI，补一份说明即可；工程上通常通过 Agent Skill（本质上是给模型看的说明文档）来完成。

总结：常见 CLI 靠预训练内化，冷门 CLI 靠文档补齐，因此 CLI 路径的 Token 成本明显低于 MCP。

## CLI 的优势二：执行效率更高

再看一个日常场景：摄影师拍完一批素材，文件夹里有 10 张照片，需要：

1. 筛出横版（宽大于高）照片  
2. 加上专属水印  
3. 上传到服务器做网页展示  

### MCP 模式下的链路

模型会反复「思考 → 调工具 → 看结果」：

1. 调读取目录工具 → 拿到 10 个文件名  
2. 调读取图片信息工具 → 拿到宽高  
3. 筛选横版后，调图像处理工具 → 加水印  
4. 调上传工具 → 传到服务器  
5. 确认全部完成 → 给出最终答复  

模型在整条链路上承担两件事：不停决定下一步调什么、传什么参数；以及每个工具结果都必须先回到模型，再决定下一步。模型成了调度中心，每一步都要等一次模型响应，效率卡在这里。

### CLI 模式下的链路

模型同样先思考，但之后只调用一次 `bash`，例如把三步串成一条流水线：

1. **exiftool**：扫描文件夹，筛出宽大于高的横版照片  
2. **ImageMagick**：逐一加水印，输出到 `output`  
3. **scp**：把 `output` 批量上传到服务器  

三步在本地自动跑完，中间不需要模型参与；全部结束后结果才回到模型，模型确认完成即可。链路短得多，效率也更高。

关键在于 CLI 可自由组合。管道 `|` 把上一步输出交给下一步；`&&` 表示上一步成功再执行下一步。几个符号就能把独立工具串成完整流程——这正是 UNIX 几十年确立的哲学：**每个工具只做一件事，但做到极致；工具之间像积木一样自由组合。**

exiftool 只管读元数据，ImageMagick 只管处理图像，scp 只管传文件，互不干涉却能协作。几行命令就能完成完整自动化，且几乎没有上限。

有人会问：把「读目录 + 读图信息 + 加水印 + 上传」做成一个 MCP 工具，一次调完，不也能达到同样效果？理论上可以，但需求稍变（只要 4K、统一转成 PNG）工具就要重写。CLI 天生是组合式的，改参数、重拼几秒就能适配；这种灵活性是 MCP 工具难以复刻的。

## MCP 的优势一：更可控

聊了这么多 CLI 的好处，并不意味着 MCP 一无是处。它能成为行业标准，也有不可替代之处，主要是两点：**更可控**、**更安全**。

更可控，说白了就是更不容易出错。前面那条看起来完美的 CLI 流水线，其实有隐患：若文件名里含单引号（如 `mark's photo.png`），可能破坏命令引号结构直接报错。这类问题在 CLI 里很常见。模型虽然擅长生成命令，但命令越复杂，出错概率越高，且错误往往很隐蔽，人工审查也不容易一眼看出。

换成 MCP，加水印时文件名通常落在 JSON 字段里。无论单引号、双引号还是空格，都有明确的转义与参数边界，不会和命令语法缠在一起冲突。因此 MCP 的执行结果更可控，出错概率也更低。

## MCP 的优势二：更安全

CLI 的灵活性是双刃剑：什么都能做，也就意味着什么都能搞砸。模型生成的命令里一旦夹带 `rm -rf` 之类操作，本地文件可能被误删——哪怕模型本意只是清临时文件。你往往执行之后才后知后觉。

本地环境里，风险或许还能自负。云端则不同：许多自动化服务（如 Make）允许在工作流里接入 MCP，但绝不会让你直接执行任意 bash。原因很简单——共享环境中，一步失控可能影响其他用户，甚至拖垮服务器或集群。

也有云端产品支持 CLI，但通常带严格沙箱与权限控制，成本高，安全等级也难与「只做设计者允许之事」的 MCP 对齐。因此在对安全性要求很高的场景下，MCP 这种受限设计反而是优势：不多也不少，只做被允许的事。

## 未来属于谁？

综合来看：CLI 比重会越来越大，MCP 比重会逐渐缩小，但不会消失。

对大多数场景和个人用户，CLI 更快、更便宜、更直接——省 Token、链路短，一行命令能搞定的事，MCP 往往要来回多轮。因此 CLI 天然偏向轻量、个人化用法。

MCP 的比例会下降，但会退守到对安全与稳定性要求更高的场景——企业与云端。那里不可能让模型自由敲命令行；结构化、可控的 MCP 调用依然不可替代。

最终格局可以概括为：**CLI 走向个人，MCP 留在企业和云端。**
